# 生产候选版设计审计与整改记录

首次审计及整改复核：2026-10-24。对象是当前工作区，不是某个已提交版本的 diff。下文第 1-5 节保留首次审计证据；整改状态以本节表格和 `docs/verification.md` 为准。

## 结论

首次审计的五项及后续复审的 R1-R6、A1 已进入实现整改。本次实现与非数据库回归已完成初验，但本机没有可用的隔离 PostgreSQL，因此迁移、事务和并发部分尚不能关闭或宣称通过。PostgreSQL 事务任务账本仍是合理候选；这些问题属于供应商契约、安全授权、运维状态机和容量隔离，改用 Redis/MQ 不会自动解决。当前仍是生产候选版，真实供应商行为、实际配额、负载、HA 和恢复能力尚未验收。

## 1. 基线发现：幂等窗口没有覆盖完整发送预算（部分整改）

证据：`notifier/production/store.py:203` 只要求 `deadline > now`，`notifier/production/runtime.py:51` 为传输配置固定 HTTP 超时，两者没有连接。`notifier/worker.py:36` 领取后直接发送，没有在出站前重验截止时间。

隔离探针把幂等任务的 deadline/key_expires_at 设置为数据库当前时间加 0.2 秒，仍成功 claim，而配置的 HTTP timeout 为 10 秒。**这证明可以在剩余预算不足时领取，不是已经复现了供应商重复扣款。**

风险：如果先前已存在一次结果不明的成功，临近窗口结束的重试可能在供应商去重记录过期后才到达。即使租约和本地写回正确，也可能重复产生副作用。

建议：区分调度截止时间、单次执行预算、供应商最晚安全接收时间；领取时预留 DNS/连接/TLS/发送及安全余量，出站前再次检查并使用剩余预算。预算不足则转核对，不继续盲发。远端接收/处理时间仍无法由本地超时严格保证，须记录供应商窗口起算规则、范围和时钟/网络假设。

验收：窗口前/后边界、领取后进程暂停、慢 DNS/TLS/写入、先前请求结果不明，均不可越过已约定的安全发送边界。

2026-10-24 后续代码复查：`claim()` 现在校验领取预算，但返回给 transport 的 request 仅有 snapshot/tenant；`Worker.run_once()` 直接发送，heartbeat 失败/租约丢失只记日志；`SupplierTransport.send()` 在 materialize 后仍使用固定 HTTP timeout，没有出站预算复核。因此领取后进程暂停再恢复仍可能越过预算边界。该结论来自静态代码检查，本轮没有注入暂停或复现重复副作用。须传递绝对安全截止时间、约束出站预算并覆盖暂停/租约丢失回归；本地检查也不能保证撤销已发送请求或消除任意时刻暂停，最终仍依赖供应商侧幂等及明确的网络/时钟/处理假设。

## 2. 基线发现：人工核对只有错误码，没有处理闭环（已整改）

证据：`notifier/production/schema.sql:24` 只有 pending/in_flight/succeeded/failed。`notifier/production/store.py:313` 的 replay 检查失败状态、预算、保留和窗口，但不要求结构化核对结论。`notifier/production/api.py:205` 只要求非空 reason。

探针：把 manual_on_ambiguous 任务置为 manual_reconciliation_required 后，operator 使用 reason=`ok` 即可重放。没有实际调用供应商。本行为不是越权，operator 本来有重放权限；缺口是无法区分“核对后确认未发生”与“仅填了原因”。

同时，`deploy/alerts.yml` 对全部 failed 任务持续告警，没有已认领/已处理的区别。`notifier/production/store.py:403` 会按保留期清理 failed 快照，未核对事项也没有独立保留策略。

建议：投递状态与处置状态分离，例如 unresolved/assigned/resolved；记录核对结论 delivered/not_delivered/unknown、证据引用、操作人及时间。已确认成功应支持“核对完成”而不是再发一次；仅确认未发生才允许安全重试，未知结果的强制重试需单独权限和风险确认。人工完成不应伪造成一次 HTTP 成功。告警统计未处理事件，保留策略明确未决事项是否暂缓清理。

验收：重复核对幂等、并发处置冲突、跨租户拒绝、已成功不可再发、未决告警可被真正解决、到期证据保留策略。

## 3. 基线发现：凭据授权过粗（已整改，仍需供应商侧最小权限）

证据：`notifier/production/config.py:104` 按 tenant + origin 授权，`materialize` 注入凭据；没有 method/path/operation 范围。

探针：授权给 `https://supplier.example` 的 crm 凭据，对同域名 `/admin/delete` 也会注入相同 X-API-Key。这不是声称该路径真实存在或已经越权访问真实系统。

风险：如凭据本来只应供订单创建使用，租户可借本服务调用同域名其他高权限接口。SSRF 防护限制网络目标，不能代替业务操作授权。

建议：版本化 SupplierProfile 定义允许的 operation、方法、规范化路径与动态参数/头白名单；凭据绑定供应商账号及契约版本，优先使用供应商端最小权限 key。路径匹配需覆盖编码、点路径、查询参数和重定向边界，不能随意添加一个宽松正则。若业务明确授予租户整个供应商账号的 API 权限，应记录这一信任决定，不把它误称为细粒度授权。

## 4. 基线发现：Retry-After 被提前截短（已整改至本地上限）

证据：`notifier/delivery.py:61` 将供应商 Retry-After 上限固定为 3600 秒。实测 `retry_after_seconds("7200") == 3600`；`notifier/production/store.py:272` 使用该值更新目标限流。

风险：供应商要求等待两小时，当前实现最早一小时后就可能重试。截断的目的是约束等待，但提前重发不能等同于尊重供应商冷却时间。

建议：区分指数退避上限与供应商最早允许再次请求的时间；后者不得因前者被提前。超出任务期限或安全窗口时应失败/暂停待处置，而不是缩短供应商等待。对畸形/极大值设置显式拒绝策略并测试。

## 5. 基线发现：多租户不等于调度公平或配额隔离（部分整改）

证据：`notifier/production/store.py:203` 按 origin 内 next_attempt_at/created_at 排序，origin 状态与熔断也是共享的。

同一 origin 先提交 acme 的 5 个任务，再提交 other 的 1 个任务，逐次完成后领取顺序为 `acme, acme, acme, acme, acme, other`。这是当前 FIFO-like 排序的预期结果；**不是无限饥饿证明**。已有测试证明的是域名间隔离，不是同域名租户间公平。

风险：共享域名下不同供应商账号、租户或接口可能有不同实际配额，却共享熔断和限流；存储配额不保证执行延迟隔离。

建议：先确认供应商真实配额维度，定义服务端控制的 delivery scope；按账号/操作配额隔离，必要时增加租户轮转或权重调度。不能直接按任意 credential_ref 分桶，否则可通过新增引用绕过供应商全局限制；需要全局与子 scope 两层预算。对首投 SLO 说明队列前置工作量和可接收突发规模。

## 7. 剩余工作顺序

1. 在隔离 PostgreSQL 上验证领取到出站的预算、租约丢失、租约过期恢复与旧 worker 写回竞争；不把数据库写回 fencing 等同于供应商外部副作用 fencing。
2. 为每个真实供应商固定 method/path/query、账号、去重窗口起算方式、结果判定和配额维度，并验证变更/撤销行为。
3. 按活跃/保留数据规模、突发、慢目标、429 冷却及多租户倾斜压测；根据安静租户等待时间和账号级配额决定是否增加 scope。
4. 补安全暂停/恢复、取消未发送任务、结构化供应商诊断和运维处置指标；高风险场景评估供应商查询 Adapter 或双人核对。
5. 用目标环境完成最小权限、非 owner 运行、滚动升级、HA/PITR、密钥恢复和真实告警演练，再决定是否可发布。成熟 PG 库可因降低维护成本提前评估，不必等到性能瓶颈；引入 MQ 则需另有明确收益和迁移证据。
