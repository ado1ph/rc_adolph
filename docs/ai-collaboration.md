## AI 提出的实现选择

1. 本机 Python 为 3.9.6，SQLite 为 3.43.2，Go 为 1.20.4，Docker daemon 未运行。用户未指定技术栈。AI 选择 Python 标准库 + SQLite，明确限定单机、loopback 演示，不要求用户安装消息中间件。
2. 业务通知与每次 attempt 分离；记录即队列，用同一存储事务避免数据库/MQ 双写。
3. 不承诺外部 exactly-once。Mock 分别提供支持和不支持幂等的既有 API，实测同样的超时重试会产生不同副作用次数。
4. 使用有限重试、失败终态与显式重放，不用“无限重试”代替运维恢复。
5. 任务 claim、attempt 与租约原子提交；用 token 和活租约阻止旧 worker 写回。明确 fencing 不能撤销外部请求。
6. 出站目标需白名单及 DNS/IP 校验；演示只显式放行 loopback，不把“内部服务”当作无 SSRF 风险。
7. 初稿采用 WAL + FULL。核对 SQLite 官方文档后，发现当前系统版本处于 WAL-reset 缺陷的潜在影响范围，修改为 DELETE + EXTRA，并加入设置验证。风险具有特定触发条件，没有夸大为一定会损坏。
8. 没有上门户、多租户、分布式调度、Kafka 或完整 webhook 平台。它们可能适合其他流量/基础设施约束，不是普遍“错误设计”。

以上为 AI 提出并执行的决策，不代表用户对每项细节作过独立选择；评审时可据此继续质询。

## 验证方法与限制

- 使用 `unittest`，既包含存储单元测试，也启动真实 HTTP API/Mock 进行端到端验证。
- 本地端口监听被 sandbox 拒绝后，经执行权限审批运行测试；没有把环境权限错误归因为业务代码失败。
- 第一轮 35 项测试通过，随后补充日志模式、存储错误、确认响应丢失、TLS hostname/IP 分离和真实 CLI 生命周期验证；最终 42 项测试在 Python 3.9.6 与 3.12.14 上分别通过。可复现结果见 `verification.md`，将来改动后的结果以实际运行 `make test` 为准。
- `make demo` 实际展示：成功 1 次、临时故障 3 次、永久拒绝 1 次、长期故障 3 次；超时场景均调用 2 次，但供应商支持幂等时副作用为 1，不支持时为 2；失败恢复后显式重放成功。
- 未做断电、磁盘损坏、真实云供应商、吞吐压测或生产安全审计。没有据此宣称生产可用。

## 生产化与架构纠偏

用户要求生产级后，AI 开始了 PostgreSQL 生产版本实现；用户随后强调先定义架构。AI 承认此前技术选择走在架构论证之前，暂停扩展，补充架构、领域词汇及两项 ADR，再按架构收敛实现。不能把真实过程改写为“一开始就先完成架构”。

最终选择是有条件采用 PostgreSQL 事务任务账本，API 与 worker 分进程部署；不引入 Redis/MQ。理由包括接收记录、幂等、任务与审计的原子提交，不仅是组件数量少。文档明确数据库热点、连接预算、清理与膨胀成本，以及达到实测边界时使用事务 Outbox 引入 MQ 的路径。

补充真实供应商不可假设支持幂等的约束：配置分为有验证时限的幂等、业务允许重复、结果不明转人工三种模式。没有承诺 exactly-once，也没有把人工核对模式描述为自动保证送达。

生产版加入租户与角色、加密、凭据引用与轮换、容量背压、共享目标限流/熔断、保留期、审计、指标、部署与运维流程。最终本地 78 项测试通过，包含真实 PostgreSQL、HTTP/TLS、独立 API/worker 和进程崩溃测试。新加初始化测试发现一个文件创建 API 误用，修复后重跑全通过。镜像构建及部署配置验证情况以 `verification.md` 为准。

“生产级”在此仍是架构和实现目标，不是已获得生产验收的认证。真实负载、HA/PITR 演练、外部幂等契约及值班告警仍需部署方完成。
