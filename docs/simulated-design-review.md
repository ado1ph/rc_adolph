# 模拟设计复盘

> **性质说明：** 本文是根据项目现有设计、实现与测试整理的面试演练材料，不是历史会话，也不是用户或 AI 的逐字记录。问答为事后模拟，不能作为原始 AI 对话提交。真实消息节选见 `ai-conversation-excerpts.md`；设计事实见 `architecture.md`、运行手册与测试。

本文按作业关注的需求理解、系统边界、可靠性与失败处理、AI 方案取舍和后续演进组织。面试时应使用自己的表达，并只陈述能够解释和举证的内容。

## 需求理解

**AI：** 题目说要尽可能可靠地把通知送达。你会给业务方承诺至少一次，还是尽量做到 exactly-once？

**候选人：** 我会先把“送达”拆开。API 返回 202，只表示服务已经把任务持久化接收，不代表供应商已经处理，更不代表后续业务完成。请求发出后如果响应丢失，供应商可能已经产生副作用；我们自己的数据库无法撤销它。因此我不承诺外部 exactly-once，也不把有限预算下的重试说成无条件至少一次。系统承诺的是可查询的持久化接收、受预算和供应商契约约束的重试，以及无法安全判断时的显式核对。

**AI：** 通用适配器怎样判断一次通知算成功？

**候选人：** 当前通用契约把 HTTP 2xx 当作供应商接口接收成功，不等同于业务操作最终成功。若某接口用 200 表示“请求已受理”，或者在响应体中携带业务失败，就需要该供应商自己的适配器和契约测试，不能靠重试通用 HTTP 请求解决。

## 架构选择

**AI：** 直接加 Kafka 或 Redis，会不会让队列更可靠？

**候选人：** 不能只看组件名称。这个服务还需要记录入口幂等、任务状态、每次 attempt、审计和人工核对。如果先写 PostgreSQL，再发布消息，就要处理数据库和 broker 之间的双写一致性；用事务 outbox 能解决原子写入问题，但仍需 relay、重复消费和运维。当前版本以 PostgreSQL 作为权威任务账本，接收和任务状态在一个事务内提交，少维护一套平台。代价是我们要承担轮询、锁竞争、索引与清理，也接受 PostgreSQL 成为共享瓶颈和故障域。

**AI：** 那是不是不应该使用消息队列？

**候选人：** 不是。作业没有给吞吐、延迟或现有平台指标，没依据说现在必须引入，也没依据说未来不该引入。我会先用代表性负载观察队龄、锁等待、数据库 CPU/IO 和拒绝率。如果账本调优后仍达不到确认过的服务目标，再用同事务 outbox 接入已有或合适的 MQ；迁移时保持单一调度权，避免两套系统同时投递。

## 失败语义

**AI：** 供应商超时了，最简单的恢复是不是再发一次？

**候选人：** 要先判断请求有没有可能到达供应商。DNS、连接或 TLS 阶段明确未发送的错误，可以在租约、截止时间和次数预算内重试。部分写入、响应丢失或供应商返回可重试状态，则可能已有副作用。只有稳定的供应商幂等 key 仍在有效窗口内覆盖下一次完整发送预算，或业务明确容忍重复时，才允许自动重试；否则进入人工核对。不能因为本地看到 timeout 就推断供应商什么都没做。

**AI：** 租约和 fencing 不能阻止重复请求吗？

**候选人：** 它们保护的是本地状态：过期 worker 不能用旧 token 覆盖新 worker 的数据库结果。已经发到外部的 HTTP 请求不受数据库事务或 fencing 控制，所以它不能消除供应商副作用。这个边界也是为什么结果不明必须独立表示、不能被后续本地错误或维护操作悄悄清除。

**AI：** 所有 5xx 都转人工，会不会太保守？

**候选人：** 保守程度由操作契约决定，而不是只看状态码。对供应商明确保证幂等、且 key 窗口足够的操作，或业务明确允许重复的操作，可以按预算自动重试；对扣款这类重复有风险、又没有可验证去重保证的操作，自动重发不合适。人工核对增加运营成本，但比把未知结果伪装成确定失败更诚实。

## 范围与安全

**AI：** 既然服务接收调用方提交的 URL，为什么不做成任意 HTTP 代理？

**候选人：** 因为内部调用方不等于安全目标。任意 URL 会带来 SSRF、DNS 解析变化、凭据误发等风险。目标授权、域名和网络地址校验、服务端凭据引用及发送前复核是这个服务边界的一部分。首版不接管所有供应商的 OAuth 刷新、动态签名和异步业务回执；出现这些协议差异时用专门的 adapter，而不是把任意转发包装成“通用支持”。

**AI：** 面试作业的 MVP 需要做成完整生产平台吗？

**候选人：** 不需要。题目主要评估判断，而不是功能堆叠。回看实现，生产版的租户权限、迁移、核对和运维文档超出了最小 MVP。面试中我会区分“作业要求”“为展示可靠性补充的实现”和“上线前仍需验证的事项”，不会把本地测试或 mock 说成真实供应商、HA 或生产负载验收。

## 验证与演进

**AI：** AI 生成了实现和测试，怎样判断结果可信？

**候选人：** 把建议变成可证伪的检查，而不是按回答写得流畅就接受。举例来说，远端 CI 曾暴露一个真实差异：传输层总超时主动中断 socket 时，异常可能被分类为普通网络错误，而非超时。我们保留发送后的不确定性和“不自动重试”断言，增加确定性回归，验证不同网络异常映射到同一超时语义，并检查租约丢失、整体预算耗尽仍优先作为本地策略错误；之后再运行全套测试和远端 workflow。

**AI：** 如果流量增长，第一步会是什么？

**候选人：** 先补需求和测量：峰值与突发持续时间、供应商延迟与限流分布、可接受排队时间、重复副作用成本、保留期限和数据库预算。然后用这些工作负载压测 API、队列年龄、锁等待和存储增长。达到明确瓶颈后再演进到 outbox 与 MQ；若只是为了让架构图更复杂就提前拆分，既没有证明收益，也会引入新的交付与运维状态。
