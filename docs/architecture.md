# 生产架构与验收边界

日期：2026-10-23。本文先定义目标和约束，再选技术。现有代码只是候选实现，是否发布由本文的验收门槛决定。未获知的业务指标标为待确认，不能由“生产级”三个字推导出无限吞吐或零故障。

## 1. 需求与假设

**已知需求**：内部系统提交供应商已有 HTTP API 的 URL、Header、原始 Body，系统异步、可靠地调用；供应商不能被要求改为订阅我们的事件格式。需支持失败恢复、查询和人工处置。

**暂定范围**：一个地域、多个可用区；可信但权限隔离的内部租户；POST/PUT/PATCH，UTF-8 Body 最大 128 KiB；无严格任务顺序；单个 HTTP 2xx 代表接收成功。真实接口若返回 200 + 业务错误，必须增加供应商 Adapter 和契约测试，不能按通用 2xx 模式上线。

**必须向业务确认**：平均/峰值提交率、突发持续时间、供应商数量与延迟分布、可接受最长延迟、关键操作重复的损失、供应商幂等保留期、现成 PG/MQ 平台、合规及地域要求、值班责任人。当前没有这些事实，以下是工程建议，不是已获批准的 SLO。

| 目标 | 建议的验收定义 | 当前证据 |
| --- | --- | --- |
| 接收可靠性 | 202 只在持久化事务提交后返回；接收失败调用方复用入口 key 重试 | 代码与故障测试，不覆盖云故障 |
| API 可用性 | 暂定月度 99.9%，排除调用方鉴权/格式/自身配额错误；容量拒绝计入服务错误预算 | 未进行月度观测 |
| 入队延迟 | 在约定负载下 p95 ≤ 200 ms；测量必须包含同步复制及 TLS | 待压测 |
| 首次投递延迟 | 健康供应商、未触发隔离/限流时 p99 ≤ 30 s；故障供应商单独统计 | 待压测 |
| 同地域故障 | 已确认提交在一次可用区故障后不丢失；要求实际同步复制及切换验证 | 本机 PG 不是证据 |
| 灾难恢复 | 暂定备份 RPO ≤ 5 min、RTO ≤ 30 min，含密钥恢复与去重核对 | 待真实 PITR 演练 |

有限重试不承诺每条任务最终成功。对供应商副作用也不承诺 exactly-once。来源业务事务和通知提交之间仍有缺口，关键业务必须在来源事务中写 outbox，由业务方 relay 按稳定 key 提交。

## 2. 逻辑与部署架构

```text
来源业务事务 ── 同事务 outbox ── 业务方 relay（业务系统负责）
                                      │ 稳定 Submission Key
                                      ▼
                       内部网关 / TLS / 入口限流
                                      │
                         无状态 API replicas ≥ 2
                     认证、租户授权、校验、准入、查询
                                      │ 短事务，提交后才确认
                   ┌──────────────────┴──────────────────┐
                   │ 专用 PostgreSQL（托管多 AZ 同步 HA） │
                   │ Job / Attempt / Audit / Quota       │
                   │ Supplier isolation / Worker lease  │
                   └──────────────────┬──────────────────┘
                                      │ 到期领取、续租、fencing
                          Worker replicas ≥ 2
                   供应商隔离、调度、协议 Adapter、超时
                                      │ 固定已验证 IP + TLS
                           出口网关 / 网络白名单
                                      │
                          供应商已有 API（不可控）

API / Worker ── 指标与脱敏日志 ── 统一监控 / 值班告警
PostgreSQL ── 加密备份 / WAL ── 异地备份
密钥管理系统 ── 只读挂载 ── API / Worker（不进入镜像与 Git）
```

代码采用模块化单体、API/Worker 两类进程，不拆成大量微服务。部署、扩容和故障隔离独立，业务状态仍由一个通知上下文拥有。数据库应专用，不与来源订单库混部；这样不能完全隔离通知自身的读写竞争，但可避免通知积压拖垮订单事务。

### Module 与 Interface

| Module | Interface 的责任 | 隐藏的 Implementation |
| --- | --- | --- |
| Admission | 鉴权后的租户提交，返回已接收/重复/冲突/超额/暂不可用 | 校验、稳定指纹、加密快照、原子配额和审计 |
| Delivery Ledger | 提交、领取、续租、完成、查询、重放 | 状态机、短事务、锁顺序、租约及过期恢复 |
| Supplier Execution | 给定不可变请求与供应商契约，返回明确分类的结果 | 凭证读取、DNS/IP 校验、TLS、HTTP deadline、结果不确定性 |
| Operations | 有权限地处置、查询与验证恢复 | 审计、分页、保留、密钥轮换、监控指标 |

不把 HTTP handler 当领域模型，也不让 Worker 拼 SQL。暂不制造“通用 MQ 接口”：PG ledger 与 MQ 的确认/事务语义不同，未来不是换一个类就能无成本迁移。

## 3. 为什么第一阶段可选择 PostgreSQL 队列

结论是**有条件采用**，理由是本题需要事务性接收、状态查询、尝试历史、租户幂等、延迟重试和重放，不是单纯发送一条瞬时消息。把权威任务与调度状态放在同一事务中，减少一个需要证明的一致性协议。PG 官方说明 `SKIP LOCKED` 可用于多个消费者访问 queue-like table，但这并非无限吞吐、严格 FIFO 或高可用的承诺。[1]

| 候选方案 | 价值 | 必须承担的代价 | 本阶段判断 |
| --- | --- | --- | --- |
| PostgreSQL ledger + 调度 | 原子接收、查询/重放/延迟与任务同事务；无需 DB→MQ relay | 自维护调度/租约；轮询、写放大、索引膨胀、vacuum、共享数据库故障域；准入串行锁是明确瓶颈 | 在验收负载能通过时采用，不宣称通用最优 |
| PostgreSQL outbox + RabbitMQ quorum queues | 专业队列确认、消费背压、独立 broker 扩展与隔离 | 增加 outbox relay、重复发布、路由确认、消费幂等、重试调度与两套平台运维；查询仍需 ledger | 团队已有平台或压力测试证明需要时优先评估 |
| 托管队列 + PostgreSQL | 减少自管 broker 负担，适合既有云平台 | 仍有 outbox、重复消费、状态一致性；可见性/延迟/配额及云依赖需按产品验证 | 部署云已确定后可替代 RabbitMQ 方案 |
| Redis 任务库 | 可复用成熟执行框架，降低自维护 worker 的成本 | 必须明确 Redis 持久化/故障切换的数据安全；仍需业务状态与入口幂等，不能只用缓存默认配置 | 没有既有平台证据，不先增加 Redis |
| Kafka 类事件日志 | 适合回放日志、多下游订阅及既有事件平台 | 本题非事件流平台；每任务不同重试时间、操作处置和任意供应商 HTTP 仍需状态与调度 | 当前需求不足以支持选它 |

不能以“MQ 会双写丢消息”否定 MQ：正确的事务 outbox 就是解决此问题的常见方案；它仍可能重复，消费者必须幂等。[2] RabbitMQ 的 publisher confirms 与 consumer acknowledgements 分别确认发布和消费；quorum queues 的可靠性还依赖多数副本可用及正确配置，不自动保证供应商只执行一次。[3][4]

### 重新选型触发条件

不是编造“超过某个 QPS 必须上 MQ”，而是看可复现实测：

- 代表性负载与两倍预期峰值下，API 延迟/拒绝率、排队延迟或 DB CPU/IO 超出预留预算。
- 准入锁等待、vacuum 压力、保留数据规模影响查询或租约续租；调优/分区后仍不能满足 SLO。
- 需要多个独立消费群、大规模扇出、跨地域活跃投递、强独立队列故障域或已有组织标准 MQ。
- 供应商增加到域名级锁/轮询扫描不可接受，或任务长期积压规模超出该 ledger 的验证上限。

届时：同一事务写 Job + Outbox → relay 发布 Job ID，等待 broker confirm 后标记 → Worker 取权威 Job 并通过 fencing 执行 → 写回结果后 ack。消费者不能仅凭 broker 消息再次调用供应商；仍需防过期/重复任务。迁移应有单一调度权开关和逐租户切换，不能让两套 scheduler 同时无约束地投递。

## 4. 数据与状态不变量

```text
pending -> in_flight -> succeeded
                    -> pending                  安全且预算内的重试
                    -> failed                   永久失败/预算耗尽
                    -> reconciliation_required  供应商结果不明或安全窗口不足
                    -> paused                   结果可按供应商契约重试，但冷却超出本地表示范围
                    -> reconciliation_required  结果不明且不能证明安全重试；证据核对后处置
reconciliation_required --delivered--> succeeded
reconciliation_required --not_delivered--> pending（仍可安全复用时）
reconciliation_required --not_delivered--> failed（明确不重试、已达重放上限、快照/key 不可安全复用）
failed --operator replay--> pending
```

1. `outcome_uncertain` 是跨 attempt 的持久化业务结果标记，与调度状态分离。可能已发送/收到可重试供应商响应、租约过期的 attempt 会在同一事务内记 attempt、标记未决并写审计。安全自动重试可在标记仍为 true 时发生；重试耗尽或后续本地授权/配置失败不能清除它，任务转人工核对且维护不删除其快照、attempt 或未决审计。只有成功供应商响应或事务性人工核对可以清除标记。后续 4xx/5xx、预发送失败和没有响应都不能证明更早 attempt 未执行。
2. Submission Key 按租户唯一；相同快照返回原 ID，不同快照 409。Supplier Key 是另一个标识，不能混淆。
3. Job 的请求快照不可变且加密；凭证使用有租户及目标授权的引用，执行时读取，支持同账号密钥轮换。快照固定供应商账号声明、授权、operation 和重试契约的 HMAC 摘要，配置漂移时 fail closed；账号声明仍须外部核实。入口请求指纹使用独立稳定 HMAC key。
4. 每次领取在同一短事务中更新 Job、创建 Attempt、占用供应商额度；事务外执行 HTTP，绝不持有 DB 锁等待供应商。
5. 完成写回只接受匹配 token 的有效租约；旧 Worker 的外部请求可能仍完成，fencing 不能撤销它。
6. 全局多副本的供应商额度、速率和熔断状态一致；origin → job 是固定锁顺序。以“域名 + 端口”隔离是保守策略，不等于供应商所有账号/接口共享真实配额。
7. 过期任务和租约有界恢复；过期 in-flight 租约按结果未决处理。无未决历史的本地预发送失败可保持普通失败；未决标记不会被重试预算、后续本地错误或任意非成功 HTTP 响应清除。
8. 普通重放仅对失败任务开放；未决结果只能由独立 reconciler 提交证据引用及结论。快照已清理返回 410，不悄悄重建。
9. 待执行数量、单租户数量、全部保留任务数量和加密快照总字节均有上限；重复提交在满载时仍可查询原接收结果。
10. 旧回执查询依赖已认证租户、规范化请求及稳定入口指纹，不依赖当前 supplier profile；首次接收和每次实际出站仍核对当前授权。
11. Worker 将领取时剩余截止预算和租约失效信号传至 HTTP 写路径；在 DNS、连接、TLS、写入及响应等待阶段遵从整体本地预算，并在业务请求写入前再次检查。单次连接/TLS 尝试超时会结束本次请求；如果整体预算和租约仍有效，它可作为可重试的预发送网络故障，后续发送必须重新领取并再次校验截止时间、租约、次数及供应商 key 窗口。确认租约失效/整体预算耗尽后，不启动新的发送；信号不能撤销正在进行或已发出的请求，任意指令点进程暂停仍有竞态。
12. `Retry-After` 的已支持数值上限为一年。更长的纯数字值令共享 origin 设置独立布尔 `cooldown_hold`，不使用非有限时间值，也不自动重发。解除 origin hold 不等于确认未送达；仅已核实 `idempotent`/`duplicate_tolerant` 任务可按预算条件恢复。历史 manual `paused` 记录由 v5 迁移保守转核对并审计。
13. 核对 API 将事实 `outcome` 与命令 `retry_after_reconciliation` 分开；响应同时给出 `retry_requested` 和 `retry_scheduled`。省略字段沿用旧客户端的“确认未送达后在预算内重试”行为；重放上限、快照/key 安全条件可以阻止调度，但不阻止记录确认事实。未排队关闭的任务不能通过普通 replay 重开。
14. 幂等模式重试需有稳定 Supplier Key，且数据库窗口覆盖计划等待时间及下一次完整本地发送预算。它只能降低重复副作用风险，保证范围取决于真实供应商契约；数据库租约/fencing 不能阻止两个 worker 在外部交错执行，亦不提供 exactly-once。
15. 清理最多每类 500 条（调用方上限 5000），用集合式 SQL 清快照/attempt 或级联删除元数据；仍与准入锁在同一事务内更新容量计数，不以代码结构推断实际延迟改善。
16. 结果确定性、核对重试决定、当前调度状态是三个独立维度。`not_delivered` 核对可解决此前 attempt 的业务歧义，但 `retry_scheduled=true` 不表示任务已终结；pending/in_flight 的当前状态、有效 lease、attempt 序号和 origin 并发计数不能由历史迁移改写。后续发送会建立新的 attempt，若再次出现歧义必须重新核对；解决旧 attempt 不代表后续任务成功。
17. v6 对历史 `retry_requested` / `retry_scheduled` 的回填来自旧状态和 `replay_count`，是推断而非原始决定。v7 新增 `retry_decision_source`：历史行使用 `legacy_unverified`，v7 之后 API 事务记录的决定使用 `runtime_recorded`。迁移不根据 v6 回填值自动关闭或恢复任务；v6 审计时间也不是业务结果证据。仅严格晚于相关 attempts 的成功/核对证据可清除旧 uncertainty；同一时间、缺失时间、冲突结论、核对后新 attempt/新歧义都保守保留。活动中的 `in_flight`、`paused` 及未决 reconciliation 状态保持原调度/租约证据；可证明的 pending/failed 结论只清 uncertainty 并保留当前状态。

## 5. 供应商契约与不确定性

必须配置重试安全模式：

- `idempotent`：供应商明确支持并已验证稳定 Supplier Key；所有尝试、重放复用同一 key。截止时间受已配置去重窗口约束，过期后拒绝重放；供应商实际去重窗口必须经过验证，不能无限相信去重。
- `duplicate_tolerant`：业务明确允许重复，例如“把联系人状态设置为 paid”；不是由 HTTP method 自动推断。
- `manual_on_ambiguous`：不能证明重复安全的操作。网络结果不确定或可重试 HTTP 错误不能盲目重复，转入独立的 `reconciliation_required` 状态；由独立核对角色记录证据和结论。确认送达关闭任务，确认未送达才恢复投递。

Mock 去重只能验证协议路径，不能证明真实供应商去重。通用 Adapter 暂只支持 HTTP 2xx 接收判据；OAuth 自动刷新、HMAC 动态签名、200 + 业务错误解析、异步业务回执需在真实供应商接入前实现并做契约测试。它们不是靠上 MQ 能补齐的能力。

## 6. 故障边界

| 故障 | 预期行为 | 不能掩盖的限制 |
| --- | --- | --- |
| API 提交前崩溃 | 无 202，调用方复用 key 重试 | 来源不重试/outbox 未落地仍会漏 |
| 提交后响应丢失 | 相同 key 返回同一任务 | 幂等元数据有保留期限 |
| Worker 崩溃/被杀 | 租约过期，其他 Worker 恢复；旧写回被拒绝 | 重复副作用仍可能发生 |
| 单一供应商卡住/限流 | 目标并发/速率/熔断限制，其他目标继续 | 并发额度必须小于整体可用执行资源，多个坏目标仍可共同占满 |
| PG 主库切换 | API 暂时 503、不假确认；Worker 等待/恢复租约 | 异步备库切换可能丢已确认事务；必须验证真实复制方式 [5] |
| 物理磁盘逼近上限 | 平台存储告警、应用配额提前拒绝 | 应用快照配额不包含索引/WAL/备份，不能替代磁盘监控 |
| 密钥/凭证不可用 | fail closed、任务保留、告警及恢复，不输出秘密 | 只备份 DB 不备份解密材料无法恢复 |
| 告警系统故障 | 平台监控 alert delivery；启动前演练实际通知 | 空接收器/示例 webhook 不等于已配置值班 |

## 7. 容量与成本

不报未经测量的 QPS。粗略需要的并发为 `提交率 × 每任务平均尝试次数 × 平均执行秒数`，还需留余量；供应商并发和速率往往先成为瓶颈。长尾、DNS、429、熔断会改变这个平均数，因此必须按供应商及故障情景测试。

例如默认 8 个执行线程、单 origin 上限 2，并不意味着能持续处理 8 个请求/秒。若某供应商平均 10 秒响应，其并发上限给出的理想吞吐只有 `2 / 10 = 0.2 次尝试/秒`，还未扣重试。此为算术示例，不是测量结果。

存储不仅是待执行任务：`日任务数 × 保留天数 × 平均快照字节`，另加加密膨胀、attempt、索引、WAL、备份及复制。保留 30 天不是免费功能；容量配额触发后必须扩容/调整保留/拒绝新任务，不绕过持久化。

第一阶段避免泛化调度平台，接受小规模准入串行锁，但必须记录锁等待。PG 并非“便宜到无成本”：需计入多 AZ 数据库、备份、监控、值班、升级、安全审计以及自维护队列状态机的工程成本。

## 8. 发布门槛

- 正确性：真实 PG 并发幂等、双 Worker 领取、进程退出恢复、过期 fencing、数据库拒绝/故障不返回 202、供应商隔离、配额、租户权限、重放审计。
- 安全：出站 SSRF/私网阻断、DNS rebinding、TLS 校验及超时，生产禁止 HTTP；密钥/凭证不进入镜像/Git/响应/日志，最小 DB 权限与网络出站策略。
- 运维：生产依赖锁定与审计、非 root 镜像、迁移与回滚、监控/真实告警联通、按供应商对账与重放流程。
- 容量：约定流量分布下正常/突发/慢目标/持续失败/保留数据量的压测，不能只在空库中测一条成功请求。
- HA/恢复：真实多 AZ 主库切换、至少两 API/Worker 副本、加密备份恢复/PITR、旧密钥恢复及业务侧去重核对。

**只有全部门槛满足，才可对指定环境和负载声明生产可用。** 当前本机测试不具备替代真实环境验收的资格。2026-10-24 最新 review 的代码项已实现，并在隔离 PostgreSQL 17.11 上通过迁移、锁/并发与状态不变量验证；供应商真实契约、账号级配额/隔离、代表性压测、HA 与恢复演练仍未验收。
